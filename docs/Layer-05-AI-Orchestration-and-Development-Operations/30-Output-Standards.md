# Output Standards

## General
All project outputs must be:
- Precise.
- Structured.
- Evidence-grounded.
- Actionable.
- Explicit about uncertainty.
- Consistent with architecture.
- Free from placeholders in final deliverables.

## Engineering Output
Include:
1. Objective.
2. Assumptions or confirmed context.
3. Architecture impact.
4. Files/modules affected.
5. Implementation.
6. Tests.
7. Security/privacy considerations.
8. Observability.
9. Migration/deployment notes.
10. Rollback.
11. Known limitations.

## Product Output
Include:
- User problem.
- Intended behavior.
- Acceptance criteria.
- Edge cases.
- Metrics.
- Dependencies.

## AI Output
Include:
- Model/tool role.
- Input evidence.
- Grounding method.
- Confidence.
- Failure modes.
- Evaluation.
- Fallback.

## Code
Code must be:
- Typed where supported.
- Linted.
- Tested.
- Validated at trust boundaries.
- Free of embedded secrets.
- Consistent with repository conventions.
- Documented where behavior is non-obvious.

## Documentation
Markdown documentation should contain complete operational detail. Final deliverables must not contain unfinished markers, empty sections, headline-only content, or deferred references in place of specifications.

## Claims
Do not claim:
- A test passed unless executed.
- A source permits use unless verified.
- A security control exists unless implemented/configured.
- A metric is achieved unless measured.
- A place fact is true without evidence.
